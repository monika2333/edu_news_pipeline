# DeepSeek 接入点下 geo_classify 全量 400（2026-11-06）

## 现象

- 每小时流水线的 `[geo_classify]` 连续报 `API 400: {"error":{"message":"This response_format type is unavailable now ..."}}`。
- 首次出现在 `pipeline_hourly_20261106_151501.log`（136 条），`154501` 涨到 241 条；当天更早的日志没有这个错误。
- 同一轮 `enrich_summary` 等其他 LLM 步骤 `ok=644 failed=0`，模型本身调用正常。

## 触发点

控制台 `llm_models` 分区在 **2026-11-06 15:14:33** 被改为七个步骤全部指向 `api-deepseek-com` 接入点（`https://api.deepseek.com`，模型 `deepseek-flash`，`api_style=thinking`）。此前默认接入点是 OpenRouter（`deepseek/deepseek-v4.1-flash-1017`），支持 `json_schema`。

## 根因

- 京内判定是七条 LLM 链路里**唯一**发送 `response_format` 的：`llm_beijing_gate.BEIJING_GATE_RESPONSE_FORMAT` 用的是 OpenAI 结构化输出扩展 `{"type": "json_schema", "json_schema": {...strict...}}`。
- DeepSeek 等原生 provider 只实现 JSON mode，不支持 `json_schema`，直接返回 400。其他步骤不带 `response_format`，所以切换后一切正常，只有 geo_classify 全灭。
- 用生产配置实测三条请求（同一 endpoint/model/prompt 形态）：
  - `json_schema` → HTTP 400，错误原文与线上一致；
  - `json_object` → HTTP 200，返回可解析 JSON；
  - 不带 `response_format` → HTTP 200，但输出不如 JSON mode 稳定。

## 连带风险

`geo_classify` 在 `beijing_gate_fail_count >= BEIJING_GATE_MAX_RETRIES`（默认 3）后会走兜底：把稿件标成 `ready_for_export`、`is_beijing_related=True`，跳过外部过滤。诊断时库里 241 篇 `pending_beijing_gate`，其中 136 篇 `fail_count=2`——再失败一轮就会被静默「按北京放行」。修复必须在下一轮 gate 执行前生效。

## 修复

`8bdcac3`：

- 新增 `llm_beijing_gate.build_response_format(endpoint)`：`api_style == openrouter` 时保留原 strict `json_schema`；其他接入点返回 `{"type": "json_object"}`。
- 字段契约本来就在 `config/prompts/beijing_gate_prompt.md` 里，且 `_parse_decision` 对缺字段/错字段会重试，所以 JSON mode 不会降低「判错就失败重试」的保障。
- 说明：能力判断借用的是 `api_style`，因为当前只有 OpenRouter/OpenAI 兼容端点支持 `json_schema`；将来新增支持该能力的接入点要显式加进 `JSON_SCHEMA_CAPABLE_API_STYLES`。

## 验证

- 新增 `test_call_beijing_gate_uses_json_object_for_json_mode_only_endpoint`；原 OpenRouter `json_schema` 用例保留。
- `tests/test_llm_beijing_gate.py` 10 passed；相关 adapter/worker 23 passed；全量 `1762 passed`（214s）。
- 用生产库配置和真实 DeepSeek 接入点跑了一次 `call_beijing_gate`：`attempts=1`，返回 `is_beijing_related=True` 且 `reason` 为合法中文 JSON。

## 后续注意

- 400 是请求错误，但 `post_chat_completion` 默认 `retry_non_retryable_statuses=True`，一次故障会按重试次数放大请求量（这次每篇打 3 次）。是否收敛尚未拍板。
- 切换接入点后如果只有单一 LLM 步骤报错，先对比该步骤是否发送了 provider 专有参数（`response_format`、`thinking`、`reasoning` 等），不要先怀疑模型或 key。
