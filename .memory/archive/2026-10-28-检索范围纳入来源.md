# 检索范围纳入抓取来源（2026-10-28，合并 b02e44b）

## 起因

用户报：搜索抽屉「全库文章检索」输入「AI时代未来教育图景 千龙网」（正文关键词 + 来源名）零结果，而不带来源时正常。

根因：`search_article_attributions` 的两条匹配路径只覆盖标题 / LLM 摘要 / 正文，**没有 `source`**：

- 原文路径：`raw_articles.title || content_markdown`
- 摘要路径：`news_summaries.title || llm_summary || content_markdown`，且要求至少一词落在 `llm_summary`

多词是逐词 AND，所以来源词永远不可能命中，整串直接归零。

实测证据（真实库）：千龙网稿件「全球妇女峰会在京开幕」（`qianlong:2025/1014/8566334`）标题含「全球妇女峰会」、正文不含「千龙网」；搜「全球妇女峰会」有结果，加「千龙网」变 0 条。对照：同一抽屉的「报送存档检索」页签早就是 title/body/source 三字段，两个页签语义不一致。

## 用户拍板（2026-10-28）

- **范围**：抽屉的全库检索 + 筛选页 / 放弃页 / 值班检索一起改（它们共用 `db_postgres_manual_reviews/_base.SEARCH_TEXT_EXPRESSION`）。
- **口径**：只纳入抓取来源 `source`。`news_summaries.llm_source`（LLM 识别的消息来源，库里 5331 篇中 3277 篇与 `source` 不同）与 `manual_reviews.manual_llm_source` 不纳入——它们是「消息来源」不是「数据来源」，混进自由文本检索后命中理由在卡片上看不见。
- **副作用**：接受检索变宽。来源名里的常见词（「北京」「日报」）会让「教育 北京」这类组合命中所有北京日报 / 北京青年报 / 北京商报稿件——这是「来源可搜」的必然结果。
- **流程**：委托书 + 变异测试。

## 实现

三处表达式各追加 `coalesce(<表>.source, '')`：

| 位置 | 字段 |
|---|---|
| `db_postgres_article_attribution.RAW_SEARCH_TEXT_EXPRESSION`（`ra`） | title + content_markdown + source |
| `db_postgres_article_attribution.SUMMARY_SEARCH_TEXT_EXPRESSION`（`ns`） | title + llm_summary + content_markdown + source |
| `db_postgres_manual_reviews/_base.SEARCH_TEXT_EXPRESSION`（`ns`） | 同摘要路径（筛选页 / 放弃页 / 值班共用同一常量） |

逐词 AND、跨字段命中、切词 / 去重 / >10 词 422、响应 `terms` 回传、摘要路径的 `llm_summary` 门槛全部未动，前端零改动。

**原文路径用 `ra.source`、摘要路径用 `ns.source`，不做跨表 `coalesce`**：trigram GIN 索引的表达式必须与查询表达式逐字一致才会被规划器选中，跨表表达式没有任何索引能对齐；而且 raw 路径只 `FROM raw_articles`，拿不到 `ns` 行。数据上两张表的 `source` 一致（join 4674 行 0 条差异），所以两者等价。

**迁移 `20261028180000_add_source_to_search_expressions.sql`：索引名保持不变，drop + 同名 create 新表达式，down 反向恢复旧表达式。** 两个原因都记在 `pitfalls.md`「数据库」节：CONCURRENTLY 在这个迁移工具链下不可用；换新索引名会让 baseline 回填用例把旧表达式索引建回来。

## 验收（委派方复跑，不只看 agent 报告）

- 全量 `pytest -q`：worktree 与 main 各 1569 passed（jsdom 真实执行）。
- 定向 4 文件 94 passed；`refresh-schema.ps1 -Verify` 12 passed。
- `SET enable_seqscan = off` + EXPLAIN：三个表达式分别命中 `raw_articles_search_expr_trgm` / `news_summaries_search_expr_trgm`（同名重建后仍是这两个名字）。
- 端到端：真实库「全球妇女峰会 千龙网」→ 1 条 `qianlong:2025/1014/8566334 | 千龙网 | 全球妇女峰会在京开幕`；「千龙网 教育」跨字段命中。
- 索引体积：一轮返工前误留了旧摘要索引（3 个 trgm 索引、库 669 MB），改成同名重建后只剩 2 个（ns 138 MB + raw 245 MB），库 534 MB。

## 测试

- `tests/test_article_attribution_search.py`：A1 仅来源词命中 / A2 标题词 + 来源词组合（本次 bug 最小复现）/ A3 只有 raw 行的文章 / A4 摘要路径隔离（两个词分别只在 `llm_summary` 与 `ns.source`，原文侧都不含）/ A5 AND 未被 OR 化（两篇各含一词，组合必须 0 条）/ A6 raw + summary 表达式断言 / A7 迁移↔表达式一致性守卫。
- `tests/test_multi_term_search.py`：B1 筛选页来源词命中、B2 来源词与标题词必须同行。

A7 是这次最值钱的用例：按下 `-- migrate:down` 把迁移切成两段，只断言 up 段里「同名 drop + 同名 create 的新表达式」，down 段的旧表达式蒙混不过去；配合 `_src_trgm` 全文不出现的断言，能捕获「索引表达式与查询表达式错位导致索引静默失效」。

## 变异（6 条全部至少让一个用例失败）

M1 raw 表达式去 source（A1/A2/A3）· M2 summary 表达式去 source（A4）· M3 `_base` 去 source（B1/B2）· M4 source 条件 OR 化（A5）· M5 迁移 up 段索引表达式漏 source（A7）· M6 `source` 换 `llm_source`（A1；注意 `raw_articles` 根本没有 `llm_source` 列，直接 UndefinedColumn，说明这个变异只能在 `ns` 侧做行为级捕获）。

- `db_postgres_news_summaries.py` 的 `SEARCH_TRGM_INDEX_SQL`（表达式的第三份副本）与 `search_news_summaries` 仍是死代码，本次按范围约束不动；它现在连索引表达式都过期了。清理任务见 `open-tasks.md`。
- `llm_source` / 人工来源的检索能力未做。要做不能塞进自由文本 AND 组，得单独做维度（例如来源过滤下拉）。
