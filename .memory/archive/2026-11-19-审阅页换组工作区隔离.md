# 审阅页换组工作区隔离（2026-11-19 交付）

## 需求

管理员（`manual_reviews`，按 `owner_user_id` 分工作区）与值班编辑（`shift_reviews`，按 `shift_id` 分工作区）在审阅页把一条新闻拖到另一个分组（京内/京外 × 正面/负面）再保存时，过去直接改写全局 `news_summaries.is_beijing_related` / `sentiment_label`——一个人换组，所有人的候选池、审阅列表、筛选、聚类都跟着变。要求：换组只在换组人自己的工作区生效；全局字段从此只由流水线写；前端交互与接口字段名不变。用户为后续自动筛选 Agent 开管理员账号铺路（它换组同样不能外溢）。

## 实现

- **存储**：迁移 `20261119120000_add_workspace_category_override.sql`，两张工作区表各加可空文本列 `category_override`（CHECK：`internal_positive` / `internal_negative` / `external_positive` / `external_negative`；NULL = 跟随全局）。单列而非「京内外 + 正负面」两列，避免半状态。只加列与约束，可回滚。
- **生效分类集中构造**：`db_postgres_manual_reviews/_base.py` 的 `review_category_expressions(alias)` 生成一对 SQL 表达式（覆盖值优先、NULL 回退 `ns` 全局），manual 包各查询与 shift adapter 都引用它；SELECT 用同名别名 `AS is_beijing_related` / `AS sentiment_label` 输出，serializer/前端零感知；筛选、计数、批量操作与聚类视图共用同一对表达式，不再手抄 CASE。
- **写路径**：`update_manual_review_order_as_user`（manual 包 `_versions.py`）与 `update_shift_review_order`（shift adapter）先读该条全局分类，用 `category_override_value` 换算：与全局一致写 NULL、不同写分组键。覆盖值与排序/状态写在**同一条 UPDATE**，before/after 行都带覆盖列，`manual_review.reorder` / `shift_review.reorder` 审计能看到覆盖值前后变化。`update_summary_categories` 删除。
- **聚类视图**：`manual_clusters` 缓存仍按全局分类构建；读取时工作区里有覆盖值的待处理条目不参与缓存簇、按生效分类以 `single-<id>` 单条出现，无覆盖值条目行为不变。缓存本身不被读取路径改写。管理员（`_clusters.fetch_manual_clusters`）与值班（`fetch_shift_clusters`）两侧一致。
- **导入**：`import_shift_reviews_into_manual` 复制 `shift_reviews.category_override`：新导入/冲突选「值班版本」按值班值写（值班无覆盖则管理员清空 NULL）；冲突选「保留现有」不动管理员覆盖值。
- **全局字段收口**：`news_summaries.is_beijing_related` / `sentiment_label` 此后只由 `geo-classify` / `enrich-summary` 写；历史值不回填、不还原，`docs/data_flow.md` 已写明。全库文章检索、归因分析、缓存构建与流水线 worker 不动，仍读全局。

## 未做 / 取舍

- **没有推进 `version + 1`**（委托书设计要求但与本项目契约冲突）：`/order` 保存后前端 `persistReviewOrder()` 不刷新 `state.reviewData` 与卡片 DOM 上的版本号，随后的 `/decide`、`/edit` 会带旧版本号；一旦 `/order` 推进版本会稳定 409。委托书同时要求前端零改动、字段名不变，故保留 `/order` 不推进版本的现有乐观锁契约（覆盖值仍与排序同一条 UPDATE 并进审计）。若要做 `version + 1`，需要前端在 `/order` 成功后应用返回的新版本号或重载列表，属于独立改动。
- 历史全局分类值不清理、不回填（按需求）。
