# LLM 4xx 错误治理（2026-11-06）

## 背景

DeepSeek 接入点切换后，京内判定发 `response_format=json_schema` 被 400 拒绝。旧链路的坏行为：

1. `post_chat_completion` 默认 `retry_non_retryable_statuses=True`，同一 400 每篇重试 3 次；
2. `geo_classify` 把 400 计入 `beijing_gate_fail_count`；
3. 三次后走“默认按北京放行”兜底，把稿件标成 `ready_for_export` + `is_beijing_related=True`，跳过外部过滤。

同一个系统性错误被摊成 241 篇文章各自的失败，且会静默制造错误分类。用户确认按「4xx 不重试 + 系统性错误不计数 + 飞书告警 + 熔断」改造。

## 交付

- `cc3598b`：类型化错误、4xx 不重试、geo 熔断与 article 级处理、飞书请求错误告警、配置项与文档。
- `22b569d`：补端点配置类错误（缺 Key / 主机白名单 / 业务配置）进熔断、run 汇总计入 systematic、409/425 去掉“假可重试”、provider_message 截断、文档范围修正。

## 设计

### 错误分类

`src/adapters/llm_chat.py` 新增 `LLMRequestError`：

- `scope=systematic`：参数/能力不支持、鉴权、模型名、请求形状等，与具体文章无关；
- `scope=article`：仅 400/413 且 message 命中上下文/长度/体积词，可能由单篇内容超限导致；
- `retryable` 只按状态码判定；临时错误不靠 `scope` 区分。

分类优先级：额度/计费（沿用 `LLMQuotaError`）> 临时（408/429/5xx）> article > systematic。

### 重试

`retry_non_retryable_statuses` 默认改 `False`；实际重试条件 =「状态码在调用方 `retryable_statuses` 中」且「属于 408/429/5xx 或网络异常」。400/401/403/404/409/422/425 一律只发一次。409/425 没有调用方放进 allowlist，若留在可重试集合只会得到“retryable=True 但从不重试”的假语义，因此按不可重试处理。

### geo_classify

- systematic / 额度 / 配置类错误（`LLMEndpointKeyMissingError`、`LLMEndpointBlockedError`、`BusinessConfigError`）：
  - 不写 `beijing_gate_fail_count`、不调 `complete_beijing_gate` 兜底；
  - 文章保持 `pending_beijing_gate`；
  - 取消未处理 future、停止后续批次，只记一条 run 级日志；
  - 飞书告警一次（同指纹冷却；额度错误走既有 quota 告警，不重复发）；
  - `run()` 重新抛出，`run_pipeline_once` 标 failed、CLI 非零退出。
- article 级 4xx：只发一次请求、只计一次文章失败；达到上限仍保持 `pending_beijing_gate`，打 `GATE EXHAUSTED`，形成待人工处理的死信，不再“默认按北京放行”。
- 临时错误：保持原重试/计数/兜底路径。
- run 汇总：`systematic=1`，`failed` 至少 +1，避免“日志 failed=0、退出码非零”。

### 飞书告警

`notify_llm_request_alert` 消息含 operation、endpoint、model、HTTP status、provider code、request id、发生时间、建议动作。配置类错误没有 HTTP 响应时显示 `no HTTP response`，provider code 用异常类名。

指纹 = status + provider code + provider message + endpoint + model（message 先去 request_id 与空白），状态写入独立 `LLM_REQUEST_ALERT_STATE_PATH`，默认冷却 1800 秒；发送失败只打印，不写状态，不影响流水线。新增环境变量已登记在 `docs/env_reference.md`。

### 异常类的一个真实坑

`LLMQuotaError` 原为 `@dataclass(frozen=True)`。RuntimeError 子类穿过 `with worker_session(...)` 时，contextlib 会做 `exc.__traceback__ = ...`，frozen dataclass 的 `__setattr__` 抛 `FrozenInstanceError`，把真正的额度错误吞掉。现已改为普通 dataclass；`LLMRequestError` 同样保持非 frozen。

## 行为矩阵

| 场景 | llm_chat | geo_classify |
|---|---|---|
| systematic 4xx | 只发 1 次，抛 `LLMRequestError(scope=systematic, retryable=False)` | 不计数、不兜底、熔断、告警、run failed |
| 配置类错误（无 HTTP） | 请求发出前抛对应异常 | 同上，告警显示 `no HTTP response` |
| article 4xx | 只发 1 次，抛 `scope=article` | 计 1 次；达上限保持 pending 死信，不按北京放行 |
| 临时错误（408/429/5xx/网络） | 按调用方 retries 重试 | 保持原计数/兜底 |
| 额度错误 | 优先 `LLMQuotaError`，不重试，quota 告警 | 熔断，不重复发请求错误告警 |

## 遗留

- 熔断 + 请求错误告警目前只接入 `geo-classify` 京内判定；其他 LLM 步骤只做到 4xx 不重试，仍按各自逐篇失败/兜底处理。
- article 级 4xx 达上限后的死信只有日志，控制台/巡检没有入口。
- 若 provider 的上下文超限用词不在 `_ARTICLE_SCOPE_MARKERS` 词表内，会被判 systematic 而熔断；方向是“宁可停下也不静默放行”，后续按实际报错扩充词表。
