# 汇总审阅预览：期号题头（2026-10-21 交付）

## 需求

汇总审阅页（`/admin/review`，值班端 `/duty` 共用同一页签）的「预览」只是正文，管理员抄进报送稿前要手写题头：

```
首都教育每日舆情综报
2026年第573期（总第3851期）
2026年10月20日
```

难点不在渲染，而在**期号怎么演进**：综报每天报送，按存档 +1 没问题；晚报只在工作日报送，但值班编辑每天做稿、期号每天 +1；且值班编辑晚上做稿、管理员第二天早上报送，日期差一天。

## 期号规则：取材日的线性函数（已用真实数据验证）

先把 `submitted_reports` 里两周的真实数据拉出来反推，结论是**期号 = 取材日的线性函数**，每个报别各一条序列，每天 +1，停报几天就跳几期：

| 报别 | 轴 | 依据 |
|---|---|---|
| 综报 | 报送日（= 取材日） | 07-30 总第3769期 → 10-20 总第3851期，差 82 天 = 差 82 期 |
| 晚报 | 取材日（= 报送日 − 1） | 07-29 取材 总第4764期 → 10-21 报送 总第4847期，差 83 天 = 差 83 期 |

用户口述里那个「看不懂」的例子其实是自洽的：周五 10/16 的稿子是 4843（取材 10/16），管理员压到周一 10/19 才报送，而**周一报送的那一份取材日是周日 10/18**，所以题头是 4845；中间 4843、4844 被跳过（周末照常吃号、周末不单独报送），这是「每天 +1」的正常结果，不是异常。

由此得到两条不变量：

- 期号在「值班编辑做稿 → 管理员报送」之间**不变**，变的只有日期行：值班编辑写制作日（= 取材日），管理员写报送日。
- 年度期号（综报的 `2026年第N期`）与总期号同步 +1；**跨年不归零**，只换年份标签（用户 2026-10-21 确认；库里 07-30 的 491 与 10-20 的 573 差 82，与总期号同步，且两数之差恒为 3278，说明没有年初归零的痕迹）。

## 设计取舍：不做计数器、不做手改、不加设置

- **否掉计数器表**（每报送一次 +1）：压稿、停报、补报、周末都会立刻错位，且要回填历史；用户例子本身就是「按报送动作 +1 会算错」的反例（周一应是 4845 而不是 4843）。
- **否掉只按工作日 +1**：10/16 的 4843 之后下个工作日应是 4844，与实际的 4845 不符。
- **最终方案**：预览时取「最近一条 `issue_no` 严格可解析、`title_line` 与标准标题一致」的归档当基准，算 `基准期号 + (目标取材日 − 基准取材日)` 的天数差。基准来自归档本身，所以压稿/停报/补报/漏录都自愈，不需要新表。
  - 严格解析是有意的：库里躺着 `总第9002期(验收测试)` 这类脏数据，宽松匹配会把基准算到 9000 期以外。
  - 天数差为 0 时（当天那期已归档）不编造下一期，只给「本期与已归档的 … 是同一期」的提示。
  - 基准超过 7 天没更新时给「已 N 天未录入新存档」的提示——漏录会让号偏小，这是唯一需要人看的异常。
- 用户明确要求：**期号不可手改、不加设置项**（2026-10-21 拍板）。所以题头只读。

## 角色口径

| 角色 | 期号轴（目标取材日） | 日期行 |
|---|---|---|
| 值班编辑（晚报） | 今天（制作日 = 取材日） | 今天（制作日） |
| 管理员（晚报） | 今天 − 1 | 今天（报送日） |
| 两端（综报） | 今天 | 今天 |

用户只在报送当天早上点预览，所以「今天」直接取 Asia/Shanghai 的当前日期即可，不需要考虑前一天晚上预览的口径。

## 前端形态（几轮验收后定稿）

- 题头**不是独立区块**，直接写进预览 textarea 的前三行 + 空行 + 正文，与正文同字体（原先做过带边框的居中区块，被否掉）。
- 底部「包含题头」开关（复用细化筛选的 switch 控件），默认开，取消后文本立刻不带题头；选择存 `localStorage.manual_filter_preview_header`。
- 备选桶不出现题头（备选不成文），前端也不发请求；无基准时题头不出现，文本框上方一行灰字说明原因；题头接口失败只丢题头，正文照常。
- 右上角 1.5rem 的 ✕（`btn-icon` + `.preview-close`），Esc 也能关。
- **Esc 必须用捕获阶段注册**（`review_tab_preview.js` 末尾）：原文抽屉/检索抽屉/查重弹窗都在 document 冒泡阶段注册了 Esc，注册得更早；预览弹窗盖在所有浮层之上，不在捕获阶段截断就会先把底下的抽屉关掉。

## 踩坑：弹窗 textarea 撑出横向滚动条

用户报「预览框要往右拖才看得全」。根因是 `.modal-body textarea` 的 `width:100%` 处于默认 `content-box`，再叠加 `padding:12px` 与 `1px` 边框后比弹窗内容区宽约 26px；`.modal-body` 只声明了 `overflow-y:auto`，按规范另一轴连带变成 `auto`，于是多出来的 26px 变成横向滚动条。
修法：`.modal-body textarea` 补 `box-sizing: border-box`（共享规则，任何弹窗 textarea 都受益）；预览文本框的内联样式收成 `.preview-text` 类，并加 `white-space: pre-wrap; overflow-wrap: anywhere`，长行按框宽折行、超长无空格串也能断。
验证方式：真实 CSS + 同一段弹窗 markup 做静态夹具，`python -m http.server` 起服务，headless Chrome 截图对比修复前后（`file:` URL 不能用，且 headless 下中文字形会重叠，属渲染兜底问题，不影响判断布局）。

## 实现落点

- `src/console/issue_sequence.py`：纯函数（解析期号、按天数差推算、三行格式化；标题行复用 `SUPPORTED_SUBMISSION_TITLES`）。
- `src/console/preview_header_service.py`：查基准（复用 `submission_archive.fetch_reports`，`limit=20` 扫最近的）、按角色定目标日期、组织响应（`lines` / `notices` / `baseline`）。
- 接口：`GET /api/manual_filter/preview-header`（管理员口径）、`GET /api/duty/shifts/{id}/preview-header`（值班口径），共用同一个 service。原先的 `GET .../preview`（`duty_review_service.build_preview`）前端从来没调用过，预览正文一直是纯前端生成，所以这次是新增薄接口而不是改它。

- 契约写进 `docs/data_flow.md`「期号（`issue_no`）」一节：`issue_no` 必须保持可严格解析，否则掉出基准。
