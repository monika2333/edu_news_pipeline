# 全站检索框统一空格分词多词检索

日期：2026-10-20。合入：23c6aab（ff-only，main 直提）。

## 背景

用户指出报送存档「手动匹配」弹窗里的 `#archive-link-q` 不支持多词检索：「我的系统中大部分页面已经支持多词，中间空个空格就可以」。要求同步改造它，并排查其余检索框，确保全局一致。

## 排查结果（改造前）

| 入口 | 状态 |
|---|---|
| 筛选页 `filter-search-input`、放弃页 `discard-search-input` | 已支持（后端 `normalize_search_terms`） |
| 全库检索抽屉 `search-q`、存档检索抽屉 `archive-search-q` | 已支持 |
| 复核页签 `review-search-input`、值班汇总 `summary-search-input` | 已支持（前端页内逐词 AND） |
| **报送存档人工回链 `archive-link-q`** | **整串 ILIKE**，本次主目标 |
| **管理页 `admin-user-search`** | **单词子串**；2026-10-08 曾拍板「不改、不要顺手统一」 |
| **原文抽屉 `content-drawer-search`** | **整串查找**（正文内高亮 + 上/下一个，不是结果筛选） |

用户书面确认：管理页搜索与原文抽屉正文检索都一并纳入本次全局统一（推翻 2026-10-08 的例外）。

## 改动

1. **链接候选后端**：`submission_archive_service.search_link_candidates` 改用 `normalize_search_terms` 切词并把 `terms` 传给 adapter（响应回显 `terms`）；`fetch_manual_link_candidates` 的 SQL 从「一个整串 ILIKE 标题或摘要」改为「每词一组 `(title ILIKE ... OR llm_summary ILIKE ...)` 组间 AND」，参数用 `sql_search.escape_like` 转义 `%`/`_`/`\`。空词列表防御性返回空页（绝不退化成无 WHERE 的全命中）。
2. **账号管理页**：`admin.js renderUsers` 改用共享 `splitSearchTerms`，逐词 AND，词可跨姓名/用户名；空串仍展示全部账号。
3. **原文抽屉两套实现**（`manual_filter/content_drawer.js`、`submission_archive/content_drawer.js`）：检索框按空白拆词，逐词高亮；命中计数与「上一个/下一个」序列包含所有词的命中。归档版在「同一位置多个词」时优先更长的词（`教育政策` 不会被 `教育` 截断）。
4. **共享切词**：`manual_filter/utils.js` 新增纯函数 `splitSearchTerms`（Unicode 空白切分、大小写不敏感去重、保留首次写法与顺序），与后端 `search_terms.normalize_search_terms` 同语义；10 词上限只在后端校验。`admin.html` 本来就加载 `utils.js`，无需新增脚本标签。
5. **文案**：三个检索框的 placeholder / aria-label 补「空格分隔多个词」。

## 设计取舍

- **为什么后端不自己切词**：全站唯一权威是 `search_terms.py`；link-candidates 直接复用它，超 10 词自然得到 422（路由把 ValueError 转 422），并自动获得大小写不敏感去重与全角空格处理。
- **为什么 SQL 不用拼接表达式**：每词一条独立 `title/summary OR` 组，保持 trigram GIN 索引可用的形态，也和存档库 `search_items` 的「逐词 AND、跨字段」口径一致。
- **正文内检索的多词语义**：它是定位工具而非结果筛选，因此多词=全部高亮而非过滤；计数从「短语命中数」变为「所有词的命中数」，这是用户确认过的预期变化。
- **管理页搜索**：单词输入行为完全不变（仍是子串匹配），只有输入多个词时才变成逐词 AND。
- 没有改复核页签/值班汇总的页内过滤：它们此前已按空白切词并逐词 AND，行为已达标，避免无关重构。
