# 2026-10-31 夜间提示词优化：波动容差 + 二次确认 + 证据计权

委托书全文用户留档；这里只记代码与 docs 看不出来的背景、取舍与生产注意事项。

## 背景：为什么要改

10-31 00:00 的 `internal_positive` 运行（90 案例、T=5、R=76、2 轮尝试）第 2 轮修好 4 条、
改坏 5 条，卡在「改坏须少于修好」。随后在生产库实测波动：81 篇各重打 2 遍 + 运行记录
共 3 个分数——约 90% 文章最大分差 0–4 分，约 10% 在
两个分位间跳 10–26 分，**5–9 分区间近乎空档**（81 篇只有 1 篇）。由此：

1. 旧检查只看过没过线，±3 分的小抖动被当成改坏（被判改坏的 5 条旧分都只比 60 高 0–3 分）；
2. 只打一次就下结论，碰巧打低的文章（「数智育人」「首都高校环境文化季」运行时 58 进了
   T，测量重打 62/64、62/61）污染待修正集，候选版本的「+8 修好」其实只是回归均值。

## 关键取舍（代码之外的「为什么」

- **判定逻辑全收在 domain**（`moved_at_least` / `case_fixed_probe` / `case_broken_probe` /
  `resolve_case_state`），worker 只编排。目的：worker 的「谁该补打」与检查的「怎么判」
  共用同一套探针，语义永不漂移；变异测试也因此能在 domain 层精确打点。
- **T 的涨幅起点不覆写 `original_score`**，做成 `fix_baseline_score` 属性（调高取两次当前
  回放较大值、调低取较小值）。`original_score` 仍指标注时/库存分，历史含义与前端「原分」
  列不变。
- **计权只动一条门槛**：「改坏 ≥ 修好计权分」才失败；「至少修好一半」「R≤max(1,10%)」
  仍按条数。标注修好 = 2、存档 = 1，改坏恒 1。
- **确认回放的成本可控**：只对「第一次就过探针」的案例补打（涨幅/降幅不足 5 分的根本不
  触发）；进 T 前确认只针对窗口内首打不达标者。实测估算：10-31 规模（T=5、R=76、2 轮）
  254 → 约 267 次（+5%）；大 T 晚（10-30 那种 T=42）约 +33%——多花的调用换掉整轮误判重跑。
- **元提示词两处修订**（去「已进入报送存档、」示例字样、自检口径加「变动不足 5 分视为
  正常波动」）与「验收判据不得写进评分提示词」拍板同源：示例里出现判据字样会被模型模仿。

## 生产注意事项

- **`config/prompts/prompt_optimizer.md` 只是文件兜底**：生产库的元提示词在
  `prompt_revisions`（key=prompt_optimizer），合并后需用户在控制台把上述两处修订同步进
  当前版本（保存会生成新 revision），否则线上优化模型仍读旧文案。
- 新字段（`current_confirm_score` / `candidate_confirm_score` / `fix_state` /
  `weighted_fixed_score` / `fluctuation_count`）只在运行记录 JSON 里，无迁移；控制台对
  历史记录按缺失容错（jsdom P10 锁定）。
- `run()` 结尾汇总改为按 outcome 分别计数（`result: revision_created=0 … check_failed=1
  error=0 preview=N`），`log_summary` 不再被本 worker 使用——`src/workers/__init__.py`
  未动，其他 worker 不受影响。
